# Method learning from study 060

This is a research-method record, not a claim of a globally new cryptanalytic algorithm or of self-modifying model weights.

## Useful capability retained

The most useful addition is an independently replayable separating-witness certificate. Every pair of the 208 initially specified transducers has a short plaintext whose two encryptions differ. All 21,528 pair witnesses were checked by separately written implementations. This proves the descriptions represent 208 distinct encryption functions; merely observing different parameter labels or searching unsuccessfully for an alias would not prove that. The certificate is a reusable validation pattern for future small finite cipher grammars, although pairwise distinguishing experiments are established mathematical practice.

The independently written reference represents the changing alphabet by its inverse mapping during decryption, unlike production's forward list. Agreement with the forward-generated tiny truth table checks both representations rather than relying only on a roundtrip within one implementation.

## What did not need improvement

The complete 480-case production benchmark used about 4.21 inclusive CPU seconds and the reference about 14.30 seconds. No search or memory bottleneck appeared in this small finite domain. A neural scorer, stochastic optimizer, learned-conflict backend or additional parallelization is not warranted by these results. Exact enumeration is simpler and gives a complete bounded outcome.

## Future-change gate

A future optimization must name a measured bottleneck or a materially different, prior-art-cleared cipher hypothesis. Preserve this frozen code and its controls; compare new implementations against complete tiny truth sets and independent outputs under a newly declared benchmark. Do not alter exchange targets, pointer arithmetic, prefix-length indexing or admission thresholds to rescue this model after a K4 negative. A synthetic validation pass demonstrates implementation correctness in this bounded task, not historical probability.

## Publication integration lesson

The broader documentation suite caught a live-frontier mismatch after four new family IDs were registered: the current CLI still loaded the 63-family historical specification. The publication update adds a separate 67-family current inventory, keeps the original 046 specification and receipts unchanged, and tests both the current register and historical reconstruction. Neither inventory grants target-launch authority. This is a navigation/reproducibility repair, not a cryptanalysis result or a change to the frozen archive.
